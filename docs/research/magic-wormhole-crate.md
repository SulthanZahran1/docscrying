# Research: `magic-wormhole` crate v0.8.1 as scry's pairing library

**Crate:** `magic-wormhole` 0.8.1 (crates.io, published 2026-05-07) — lib package of the workspace at github.com/magic-wormhole/magic-wormhole.rs (repo main commit referenced: `41d78aed`, 2026-07-22). The CLI lives in the same repo under `cli/` (package `magic-wormhole-cli`, binary `wormhole-rs`).
**Sources:** crate tarball `magic-wormhole-0.8.1.crate` from static.crates.io (extracted locally; all `src/…` paths below refer to it), `cli/src/main.rs` from the repo checkout, docs.rs, EUPL-1.2 text in `LICENSE`, protocol specs (magic-wormhole-protocols `transit.md`), and empirical `cargo build --target wasm32-unknown-unknown` runs.

## 1. Library API for scry's native (server) side

Everything needed is public at crate root (`src/lib.rs` re-exports): `AppConfig`, `AppID`, `Code`, `MailboxConnection`, `Mood`, `Nameplate`, `Password`, `Wormhole`, `WormholeError`, `rendezvous`, plus `transit` (feature `transit`) and `forwarding` (feature `forwarding`).

- **Custom AppID + custom rendezvous URL** — `AppConfig<V>` (`src/core.rs:506-536`) has public fields `id: AppID`, `rendezvous_url: Cow<'static, str>`, `app_version: V`, with builder methods `id()`, `rendezvous_url()`, `app_version()`. `AppID::new(id)` (`src/core.rs:551`). The rendezvous URL is a WebSocket URL; default is `rendezvous::DEFAULT_RENDEZVOUS_SERVER = "ws://relay.magic-wormhole.io:4000/v1"` (`src/core/rendezvous.rs:18`). Protocol-level note: "Two clients that are connected to each other need to know beforehand how to communicate with each other once the connection is established… Clients with different AppIDs cannot communicate" (`src/lib.rs:9-10`). scry can use any `AppID` (e.g. `com.scry/pair`) and any mailbox URL; it does **not** have to use the default server.
- **Allocate a nameplate (sender side)** — `MailboxConnection::create(config, code_length)` allocates nameplate + password and returns the connection; `mailbox_connection.code()` gives the `Code` to display (`src/core.rs:115-121, 259-262`). `MailboxConnection::create_with_password(config, password)` for a fixed password (`src/core.rs:145-150`).
- **Join with a code (receiver side)** — `MailboxConnection::connect(config, code, allocate)` where `code: Code` parses via `FromStr` (`src/core.rs:196-223, 876-891`); `allocate=false` fails with `WormholeError::UnclaimedNameplate` if the nameplate doesn't exist (checked via `list_nameplates()` first, `src/core.rs:207-213`).
- **Complete SPAKE2** — `Wormhole::connect(mailbox_connection)` performs the PAKE, key confirmation and version exchange (`src/core.rs:286-341`; key exchange in `src/core/key.rs`, `make_pake`/`extract_pake_msg` via the `spake2` crate, dependency `spake2 = "0.4.0"` in Cargo.toml). Afterwards `Wormhole::send` / `receive` / `send_json` / `receive_json` give an encrypted message pipe (`src/core.rs:343-413`); `wormhole.key()` exposes the session key from which a transit key is derived (`derive_transit_key`, used at `src/forwarding.rs:212`).
- **App-level protocol versioning** — `app_version: V` is exchanged during the Wormhole handshake and is app-defined; `Wormhole::peer_version()` returns the peer's (`src/core.rs:465-467`). This is the mechanism by which scry and its browser client negotiate.
- **Server shutdown** — `Wormhole::close()` / `MailboxConnection::shutdown(Mood)` report a `Mood` (`happy`/`lonely`/`errory`/`scared`) to the server (`src/core.rs:416-419, 474-493`).

Minimal server-side flow (from the crate's own doc examples, `src/core.rs:108-114, 186-195`):

```rust
let config = AppConfig { id: AppID::new("com.example.scry/pair"),
                          rendezvous_url: "ws://relay.magic-wormhole.io:4000/v1".into(),
                          app_version: /* your version struct */ };
let mailbox = MailboxConnection::create(config, 2).await?;   // sender: allocates nameplate
// display mailbox.code() to the human
let wormhole = Wormhole::connect(mailbox).await?;             // SPAKE2 completes here
// wormhole.send_json(...) / receive_json::<T>() ... then close
```

## 2. Port-forwarding pattern (`forwarding` module)

The `forwarding` module (`src/forwarding.rs`, feature `forwarding = ["transit", "dep:rmp-serde", "dep:async-process"]`) is a client-to-client protocol that multiplexes TCP connections over a transit channel, keyed by its own AppID `piegames.de/wormhole/port-forwarding` (`src/forwarding.rs:30-46`). Doc comment: "It is bound to an APPID, which is distinct to the one used for file transfer. Therefore, the codes used for port forwarding are in an independent namespace" (`src/forwarding.rs:6-7`).

- **Serve side (exposes localhost services to the peer):** `forwarding::serve(wormhole, transit_handler, relay_hints, targets, cancel)` — `targets: Vec<(Option<url::Host>, u16)>`; `None` host means the local port (forwarded to the peer as `localhost`, `[::1]` on connect, `src/forwarding.rs:375-378`); `Some(host)` forwards a *remote* host which the code warns is broken for HTTP ("Due to HTTP being host-aware this will very likely fail!", `src/forwarding.rs:182-184`). Runs until error/peer close/`cancel`; pass `futures::future::pending()` to run forever (`src/forwarding.rs:143-146`).
- **Connect side (the reader's machine):** `forwarding::connect(wormhole, transit_handler, relay_hints, bind_address, custom_ports)` returns a `ConnectOffer` with the port mapping (`offer.mapping: Vec<(u16, Rc<String>)>`); the caller must call `offer.accept(cancel)` or `offer.reject()` (`src/forwarding.rs:520-540, 660-743`).
- **CLI usage as reference:** `wormhole-rs forward serve [DOMAIN:]PORT…` calls `forwarding::serve(wormhole, &transit_handler, relay_hints, targets, ctrlc_handler())` in a spawned task (`cli/src/main.rs:486-512`); `wormhole-rs forward connect [-p PORT] [--bind ADDR]` calls `forwarding::connect(…)` then `offer.accept(ctrlc_handler())` (`cli/src/main.rs:514-551`). Both sides use `forwarding::APP_CONFIG` (default rendezvous) with `app_version.transit_abilities` set from CLI flags (`cli/src/main.rs:487-488, 526-527`).
- **For scry:** yes, this is directly usable as a library to expose a localhost doc-reader HTTP server to the remote reader. Caveat: **both sides must run the same app protocol** — the remote reader side must also speak the `forwarding` protocol (i.e. the browser client must implement or reuse `forwarding::connect`), because the protocol uses its own AppID and its own msgpack peer messages (`PeerMessage` enum, `src/forwarding.rs:968-999`). The forwarding module is native-only: it unconditionally uses `async_net::TcpListener/TcpStream` (`src/forwarding.rs:19, 379, 635`) — see §3.

## 3. wasm32-unknown-unknown

- **The crate compiles for wasm** with the features scry needs for pairing + data (`transit, transfer`): upstream CI builds `--target wasm32-unknown-unknown --no-default-features --features transit,transfer` (`.github/workflows/push.yml` WASM matrix entry), and I reproduced a clean `cargo build --target wasm32-unknown-unknown --no-default-features --features transit,transfer` of v0.8.1 locally (Rust 1.97.1) — succeeded. CI explicitly **skips the `forwarding` feature on WASM** (`if: ${{ matrix.os != 'WASM' }}` on the forwarding build step) — and my local `cargo build --target wasm32-unknown-unknown --no-default-features --features forwarding` of 0.8.1 **fails** (`use of unresolved module or unlinked crate 'async_net'` in `src/forwarding.rs` — the module is not cfg-gated for wasm). So: browser = no `forwarding` module today; scry's browser side cannot use `forwarding::connect` as-is.
- **Wasm transport story:** the crate has explicit wasm plumbing — `cfg(target_family = "wasm")` deps `ws_stream_wasm 0.7.3`, `wasmtimer`, `getrandom/js` (Cargo.toml); `WsConnection` is a `ws_stream_wasm::WsStream` on wasm vs `async_tungstenite` on native (`src/core/rendezvous.rs:90-99`), and the mailbox connect uses `WsMeta::connect` on wasm (`src/core/rendezvous.rs:361-368`). For transit, wasm can only use the **websocket relay** path: `connect_ws_relay` (`src/transit/transport.rs:262-281`); direct TCP is compiled out on wasm (`TcpListener/TcpStream` are `#[cfg(not(target_family = "wasm"))]`, `src/transit.rs:19-20`). In `connect_inner`, the wasm branch connects only to `hint.ws` endpoints (`src/transit.rs:1231-1273`); native additionally tries `hint.tcp` (`src/transit.rs:1187-1229`). `TransitInfo.peer_addr` doesn't exist on wasm (`src/transit.rs:648-651`).
- **Known wasm blocker in 0.8.1:** `src/transit.rs:32` imports `std::time::Instant` unconditionally; `std::time::Instant` is unavailable on `wasm32-unknown-unknown` in practice. Upstream CI only runs `cargo build` (not `cargo test`) for WASM, and the build passed for me — but a **working browser app requires a patch**: lucamartinetti/wormhole-page (a browser file-transfer app, github.com/lucamartinetti/wormhole-page, "Your browser runs a full Magic Wormhole client via WebAssembly (compiled from wormhole-rs)") pins a 1-commit fork branch `wasm-time-fix` of magic-wormhole.rs ("fix: cfg-gate std::time::Instant for WASM targets", commit `b695a1d`, 2026-03-19) that gates the import and skips the "wait for better direct connection" optimization on wasm. This fix is **not** in the 0.8.1 release (verified in the crate source). scry will need this patch (or the upstream PR when merged) for a browser build.
- **Browser transit flow requires a WS relay/bridge:** browsers cannot open raw TCP; the wasm transit path connects to a relay via `ws://`/`wss://` WebSocket. wormhole-page demonstrates the pattern: the browser uses a `ws://` bridge URL pointing at the app's own server, which forwards to the public TCP transit relay, and the client advertises **both** `ws://bridge` and `tcp://transit.magic-wormhole.io:4001` in one `RelayHint` so the native peer connects via TCP while the browser connects via the bridge (`relay_hints()` in wormhole-page `crates/wormhole-wasm/src/lib.rs`). This is an app-level bridge, not part of the crate. Browser→browser works through the same relay. (Warp, Wyrmhole, Wormhole File Transfer are native desktop/mobile apps using the crate as a library — README "Applications using Wormhole Rust as library" — only wormhole-page is wasm.)

## 4. Transit

- **When is a relay required:** transit first tries direct TCP between peers (STUN-learned public IP + local interface hints, `src/transit.rs:742-831`); the leader waits briefly for a direct connection even after a relay connects, and prefers it ("Established transit connection over relay. Trying to find a direct connection …", `src/transit.rs:977-1009`). If no direct connection succeeds (both sides behind NAT/firewalls, or wasm where direct is impossible), both sides connect to a relay which glues the streams ("transparently glue the connections together", `src/transit.rs:7-9`; spec: magic-wormhole-protocols `transit.md`). Abilities control this: `transit::Abilities { direct_tcp_v1, relay_v1 }` with presets `ALL`, `FORCE_DIRECT`, `FORCE_RELAY` (`src/transit.rs:143-189`); `FORCE_RELAY` hides your IP from the peer. Handshake is asymmetric: one side `TransitRole::Leader`, the other `Follower` (`src/transit.rs:865-874, 909-926`); in the `forwarding` protocol the serve side is Leader and connect side is Follower (`src/forwarding.rs:211, 580`).
- **Protocol version:** `relay-v1` (the crate serializes abilities as `[{"type":"direct-tcp-v1"},{"type":"relay-v1"}]`, `src/transit.rs:223-247`). Relay handshake: client writes `please relay {hex-hkdf-token} for side {hex}\n` and awaits `ok\n` (`src/transit.rs:1444-1455`; token derived with HKDF context `transit_relay_token`; spec `transit.md` "Relay Handshake (relay-v1)"). Encryption on the wire is NaCl secretbox (noise-crypto is compiled out, `can_noise_crypto() -> false`, `src/transit.rs:206-209`).
- **Rust transit relay server implementation:** **none maintained.** The official relay is Python: github.com/magic-wormhole/magic-wormhole-transit-relay (MIT, Twisted, `twistd3 transitrelay`; "helps clients establish bulk-data transit connections even when both are behind NAT boxes… Two connections with identical handshakes are glued together"). There is a Rust prototype, sigwinch28/magic-wormhole-transit-relay-server.rs ("prototype replacement… [x] new: `please relay ${token} for side ${side}`", i.e. the current handshake), but it's a prototype with unimplemented features (auth, usage stats, pruning). The mailbox/rendezvous server is also Python: magic-wormhole-mailbox-server (MIT). So a self-hosted scry stack would run the Python servers (or the prototype relay) — or use the public `relay.magic-wormhole.io` / `transit.magic-wormhole.io` servers.
- **Websocket transit URL config:** relay hints are constructed with `transit::RelayHint::from_urls(name, urls)` where each URL scheme may be `tcp` (→ `hint.tcp`) or `ws`/`wss` (→ `hint.ws`) (`src/transit.rs:489-522`; `RelayHintParseError::UnknownSchema`: "Currently known values are 'tcp', 'ws' and 'wss'"). Serialized wire form: `{"type":"relay-v1","name":…,"hints":[{"type":"direct-tcp-v1","hostname":…,"port":…},{"type":"websocket","url":…}]}` (test at `src/transit.rs:1484-1523`). Defaults: `transit::DEFAULT_RELAY_SERVER = "tcp://transit.magic-wormhole.io:4001"` (`src/transit.rs:41`); the CLI takes `--relay-url` for the mailbox and `--relay-server` (repeatable) for transit hints, defaulting to `DEFAULT_RELAY_SERVER` (`cli/src/main.rs:119-128, 617-626`). The wasm client uses the `ws`/`wss` entries; the native client can use either.

## 5. License: EUPL-1.2 and scry

- Crate license is `EUPL-1.2` (Cargo.toml; LICENSE is the EUPL v1.2 text). README adds: "This work is licensed under the EUPL v1.2 or later. Contact the owner(s) for use in proprietary software."
- EUPL is a **copyleft license**: Article 5 "Obligations of the Licensee", "Copyleft clause": "If the Licensee distributes or communicates copies of the Original Works or Derivative Works, this Distribution or Communication will be done under the terms of this Licence or of a later version of this Licence… The Licensee (becoming Licensor) cannot offer or impose any additional terms or conditions on the Work or Derivative Work that alter or restrict the terms of the Licence."
- **Derivative-work definition** (Article 1): "'Derivative Works': the works or software that could be created by the Licensee, based upon the Original Work or modifications thereof. This Licence does not define the extent of modification or dependence on the Original Work required in order to classify a work as a Derivative Work; this extent is determined by copyright law applicable in the country mentioned in Article 15." So whether statically linking the crate into scry makes scry a derivative work is decided by copyright law (per Article 15 jurisdiction), not by the EUPL itself — standard copyleft analysis applies: linking the (modified or unmodified) library into a distributed binary is generally treated as creating a derivative work, which would put scry's distribution under EUPL-1.2 (or a later version) with the corresponding source-availability obligations (Article 3: "Communication of the Source Code" — must be available to licensees).
- **Compatibility clause** (Article 5): derivative works "based upon both the Work and another work licensed under a Compatible Licence" may be distributed under the compatible licence. The Appendix's "Compatible Licences" list: GPL v2/v3, AGPL v3, OSL 2.1/3.0, EPL 1.0, CeCILL 2.0/2.1, MPL 2, LGPL 2.1/3, CC BY-SA 3.0 (non-software), EUPL 1.1/1.2, LiLiQ-R/R+. **MIT and Apache-2.0 are not in the list** — so scry cannot simply stay MIT/Apache if it distributes a derivative work of the EUPL crate; a compatible license (e.g. GPLv3/AGPLv3, or EUPL itself) would be required, or a license-advice review of whether mere dynamic linking avoids derivative-work status.
- **CLI relevance:** the CLI package `magic-wormhole-cli` is part of the same workspace and "license.workspace = true" → also EUPL-1.2 (`cli/Cargo.toml`). It matters only if scry copies CLI code (e.g. the forwarding CLI wiring in `cli/src/main.rs`); depending on the crate alone is what triggers the copyleft analysis above. Note: the crate is **not** on the SPDX/GitHub-recognized "permissive" path, and EUPL's copyleft applies on distribution/communication, not on internal use (Article 2 grants "use the Work in any circumstance and for all usage").
- **Caveat:** this is a factual summary of the license text, not legal advice; the derivative-work extent clause explicitly defers to national copyright law (Article 15), so a lawyer should confirm scry's licensing choice.
